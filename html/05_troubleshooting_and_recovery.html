第5章：トラブルシューティングとリカバリー方法

チーム開発を進めていると、必ずエラーや予期せぬ状況に遭遇します。 ここでは、最もよくあるトラブルである「コンフリクト（衝突）」の解消法と、操作を間違えたときの「やり直し（リカバリー）」コマンドについて解説します。

5.1 コンフリクト（衝突）が発生したとき

Q. コンフリクトとは？

AさんとBさんが、「同じファイルの、同じ行」を同時に書き換えて、それぞれを合流（マージ）させようとしたときに発生します。 Gitは「どちらの変更を採用すべきか自動で判断できない」ため、エラーを出して人間に判断を委ねます。

解決手順

  1. git pull や git merge を実行した際、画面に CONFLICT (content): Merge conflict in <ファイル名> と表示されます。
  2. 競合が発生したファイルを開くと、以下のような競合マーカーが挿入されています。

```javascript <<<<<<< HEAD console.log("Aさんが書いたログイン画面"); ======= console.log("Bさんが書いたログイン画面");

feature/#13-another-login ```

  • <<<<<<< HEAD から ======= まで：現在のブランチ（自分側）のコード

  • ======= から >>>>>>> まで：取り込もうとしているブランチ（相手側）のコード

  • 手動で修正する: 関係メンバーと相談し、どちらのコードを残すか（あるいは両方を組み合わせるか）を決め、不要なコードとマーカー（<<<<<<<, =======, >>>>>>>）をエディタ上で綺麗に削除します。

修正後: javascript console.log("相談して決めた正しいコード");

  1. 修正をコミットする: ファイルを保存し、以下のコマンドでコンフリクト解消を完了させます。

bash git add <コンフリクトを直したファイル名> git commit -m "fix: コンフリクトの解消"

5.2 作業ブランチに最新の main を取り込む方法

自分が作業している間に、他のメンバーの変更が main に次々とマージされ、手元のブランチが古くなることがあります。 このままだと、後からプルリクエストを出したときにコンフリクトを引き起こす可能性が高くなります。

定期的に、作業中のブランチに最新の main の変更を取り込むようにしましょう。

# 1. 自分の作業ブランチにいることを確認する
git status

# 2. リモート(origin)の最新の main を、直接自分のブランチに合流させる
git pull origin main
  • ※もしここでコンフリクトが発生したら、上記の「5.1」の手順で解決します。

5.3 やらかしたときのレスキューコマンド集（安全弁）

Gitの操作やエディタでの編集を間違えたとき、パニックにならずに戻すためのコマンドです。

ケース 1：ファイルの編集をすべてなかったことにして、前回のコミット状態に戻したい

  • 状況: コードを書き換えたが、バグだらけになったので一旦全部綺麗に消してやり直したい！
  • コマンド: bash git restore <ファイル名>
  • ※すべての変更ファイルを元に戻したい場合は git restore . を実行します。一度実行すると、保存していない書き換え内容は復元できないので注意してください。

ケース 2：間違えて git add してしまったファイルを取り消したい

  • 状況: コミットに含めたくないファイル（関係ないメモなど）を誤って git add してしまった！
  • コマンド: bash git restore --staged <ファイル名>
  • これを実行すると、ファイルの中身は変更されず、ステージングエリア（コミット待ち台車）から下ろすだけになります。

ケース 3：コミットした直後に、メッセージのタイポや小さな修正忘れに気づいた

  • 状況: git commit をした直後、スペルミスや1行の消し忘れに気づいた。もう一度別のコミットを作るのは格好悪い……。
  • コマンド:
  • 忘れていた修正があれば、ファイルを直して git add <ファイル名> を行う。
  • 以下のコマンドを実行する。 bash git commit --amend -m "正しい新しいコミットメッセージ"
  • 直前のコミットが上書き修正され、綺麗な履歴になります。（すでに git push してしまったコミットに対しては行わないでください）

ケース 4：コミット自体を完全にキャンセルしたい（ファイルは残す）

  • 状況: コミットしたが、やっぱりもう一度 add するファイルを選び直したい。
  • コマンド: bash git reset HEAD~1
  • 直前のコミットが取り消され、コミットされていたファイルは「addする前の状態（ワークツリー）」に戻ります。書いたコードは消えないので安心してください。

5.4 【超重要】やってしまった！機密情報（パスワードやAPIキー）をプッシュしたとき

開発中、誤ってパスワードやAPIキーなどの機密情報をコミットし、GitHubにプッシュ（送信）してしまうことがあります。

🚨 Caution

最優先：まずい情報を「即座に無効化（再発行）」する GitHubにプッシュされた情報は、数秒以内にクローラー（自動巡回ロボット）によって検知・悪用される可能性があります。Gitの歴史から消す作業よりも前に、漏洩したパスワードや鍵を無効化（ローテーション）することが最優先です。「歴史から消したから安心」と考えてはいけません。

その上で、以下の手順でGitの履歴から機密情報を完全に消去します。

パターンA：どのコミットに入ったか分からないが、まだマージ前のブランチの場合

「何回もコミットを重ねてしまい、どのコミットに機密情報を含めてしまったか分からない」という場合は、履歴のクリーンアップ（初期化）が最も安全で簡単です。

  1. main の時点まで履歴を巻き戻す 作業ブランチにいる状態で以下を実行します。 bash git reset main
  2. 何が起きるか: このブランチで行った過去のコミット履歴がすべて消去され、main と同じ状態に巻き戻ります。

  3. 安心ポイント: あなたが書いた最新のコードは消えずにそのまま手元に残ります（git status で赤文字で表示されます）。

  4. 機密ファイルを手動で削除 ＆ .gitignore に登録する

  5. 例：誤ってコミットしていた .env ファイルなどを削除するか、プロジェクト外の安全な場所に退避させます。

  6. .gitignore に除外設定（例：.env）が書かれているか確認します。

  7. 綺麗な1つのコミットとしてやり直す bash git add . git commit -m "feat: 機能実装（履歴をクリーンアップ）"

  8. GitHubへ強制プッシュ（フォースプッシュ）する bash git push origin <現在のブランチ名> -f

  9. これにより、GitHub上の「汚れた履歴」が、今ローカルで作った「綺麗な履歴」に丸ごと上書きされ、機密情報は歴史から完全に消え去ります。

パターンB：すでに main ブランチにマージされてしまった場合

他のメンバーもその main を取得しているため、個人の判断でフォースプッシュを行うとチーム全員のGit履歴が壊れます。通常の削除コミットを作っても、過去の履歴（コミットログ）を遡れば機密情報が見えてしまいます。

  1. 即座に機密情報を無効化（最優先）
  2. チームのリーダーや管理者に報告し、git-filter-repo などの専用ツールを用いて、リポジトリの全歴史から該当ファイルを完全に抹消する作業を依頼してください。
