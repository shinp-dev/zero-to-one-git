# 第10章：AIと進める開発 — 依頼・確認・引き継ぎ

## この章のゴール

**AIに編集やGit操作を任せ、目的・差分・検証結果から変更を採用するか判断できる。**

AIを使うために全コマンドを暗記する必要はありません。第0〜2章で「どこへ何を記録するか」を押さえたら、この章の依頼例で第7章の演習を進められます。AIを使わずに進めても、到達目標は同じです。

## 1：任せる仕事と判断すること

| 場面 | AIへ任せられる仕事 | 人間が押さえること |
|---|---|---|
| 着手 | 現状調査、修正案、Issue本文の下書き | 目的、完了条件、対象範囲 |
| 実装 | 編集、branch作成、commit、検証 | 既存の変更を混ぜず、目的に合う変更か |
| 提出 | push、PR作成、差分の説明 | 提出先、実際の差分、検証の根拠 |
| 統合 | レビュー修正、許可されたmerge | 未確認事項を踏まえて採用できるか |

最初に「PR作成まで」「確認が通ればmergeまで」など任せる範囲を決めます。その範囲内の操作を毎回手動で承認する必要はありません。履歴の書き換えや既存作業の破棄など、合意した範囲を超える操作は別途判断します。

## 2：そのまま使える依頼例

次は第7章のプロフィール演習用です。OWNER/REPO、Issue番号、プロフィールの内容は自分のものに置き換えます。Issueは先に作成してください。

```text
対象: OWNER/REPO
Issue: #12 プロフィールを追加する
目的: チームメンバーが担当と学習内容を確認できるようにする。

最初にリポジトリの作業ルール、現在branch、未commit変更、remoteを確認してください。
既存の変更がある場合は勝手に破棄・commitせず、今回の作業から分離してください。
最新のorigin/mainからfeature/issue-12-add-profileを作ってください。

profile_template.mdを使い、profiles/taro.mdだけを追加してください。
記入内容:
- ニックネーム: taro
- 役割: 学習メンバー
- 学習中の技術: Git
- ひとこと: PRの流れを練習中です
- 最近取り組んでいること: Gitのbranchとcommitの違いを学ぶ
- 更新ログ: 作成日を記入

完了条件:
- 必須項目が埋まり、プレースホルダーが残っていない
- テンプレートと他のプロフィールを変更していない
- 不要な個人情報や秘密情報を含まない

内容と差分を確認し、commit・push・main向けPR作成まで進めてください。
PRにCloses #12と実施した確認結果を書いてください。
mergeはまだ行わないでください。
最後にbranch、commit ID、PRのURL、確認結果、未確認事項を報告してください。
```

チャットへの助言だけを行うAIは、ファイル編集やpushを実行できません。その場合は提案を自分で実行します。実行できない確認は「未実施」として扱い、「成功」と書かせないことが大切です。

アプリ開発では「必須項目」の代わりに、具体的な入力・期待する結果・既存機能への影響を指定します。AIが提案した完了条件も、利用者の目的に合っているか見直します。

## 3：完了報告を実物と照合する

まず、AIが作業したリポジトリとbranchにいることを確認します。以下はbaseがmainの例です。

```bash
git status
git branch --show-current
git diff
git diff --staged
git fetch origin
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
```

- `git status`と2つの通常のdiffは未commitの作業を確認するものです。未追跡ファイルの中身は開いて確認します。
- `git diff origin/main...HEAD`は、mainとの共通祖先から現在のcommitまでの変更を確認します。未commit変更は含みません。
- 別のPCやクラウド上でAIが作業した場合、手元のHEADは更新されていません。まずPR上の差分を確認するか、作業branchを取得して正しい場所へ移動します。

push後は、PRのbase / compareとFiles changedを確認します。CLIなら次を使えます。

```bash
gh pr view
gh pr diff
gh pr checks
```

AIの要約と実際のファイル一覧が合わない場合は、差分を基準に調べます。PRへ追加commitが入った場合は、その変更も確認します。

### 検証結果の読み方

「テスト成功」だけでは判断材料が足りません。何を、どの変更状態で確認し、何が未確認かを残します。

| 報告 | 判断できること |
|---|---|
| 「問題ありません」 | 何を確認したか分からない |
| 「プロフィールの全項目とPR差分を確認。追加は1ファイル。GitHubでの表示確認は未実施」 | 内容の確認範囲と、残る表示確認が分かる |
| 「対象機能のテストは成功。実機での操作は未実施」 | 自動確認と実機確認を分けて判断できる |

この教材にはCI workflowがありません。CIチェックがないことを成功と解釈せず、Markdownの表示と内容を確認してください。コードの変更では、必要に応じて既存テストや動作確認を使います。AIが実装と一緒に作ったテストも、期待する仕様を確かめているか確認します。

## 4：AIと並行作業する場合

**同じフォルダでbranchだけを切り替えても、作業者ごとの隔離にはなりません。** 未commitの変更やstagingを共有してしまいます。最初は1作業ずつ進め、並行作業が必要なら別cloneか`git worktree`で作業フォルダを分けます。

発展例として、既存の作業フォルダからAI用フォルダを追加します。branch名とフォルダ名が未使用であることを確認してください。

```bash
git fetch origin
git worktree add -b feature/ai-profile ../zero-to-one-ai-profile origin/main
git worktree list
```

AIには追加したフォルダを作業先として渡します。各worktreeは編集ファイル・staging・HEADが分かれますが、Gitの履歴やbranchなどは共有します。これだけで秘密情報や実行環境が隔離されるわけではありません。同じファイルを変更する作業は、担当範囲や統合順も決めてください。

片付けは、必要な変更がcommit・push・統合済みで、未commit・未追跡の必要なファイルがないことを確認してから行います。

```bash
git worktree remove ../zero-to-one-ai-profile
```

削除を拒否されたら理由を確認し、安易に`--force`を付けません。branchの削除は第4・9章の手順で別に行います。

## 5：中断・失敗から再開する

AIとの会話が切れても、GitとPRに再開材料を残せます。

- 対象repo、branch、最後のcommit ID、PRのURL
- 完了したことと残っていること
- 実施した確認と未確認事項
- 未commit変更の有無、次に行う作業

再開時は、この報告を現在の`git status`やPRの状態と照合します。「続きをやって」だけで古いbranchを操作しないようにします。

誤った変更を見つけた場合は第6章へ戻り、未commit・未共有commit・共有済みcommitを区別して戻します。`reflog`は未commitの編集をすべて復元する仕組みではありません。着手前の作業を残しておくことが大切です。

## 完了チェック

- [ ] AIへ目的・範囲・完了条件・任せる操作を伝えた
- [ ] 未commit変更とcommit済みの提出差分を区別して確認した
- [ ] AIの報告と実際の検証結果を照合した
- [ ] PRの追加commitも含めて採用を判断できる
- [ ] 中断後に再開するための情報を残せる
