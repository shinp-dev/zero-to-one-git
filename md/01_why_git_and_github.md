# 第1章：なぜGit/GitHubが必要なのか

## この章のゴール

**ブランチ・Issue・PRが、どの問題を解決するのか説明できる。**

## まず見る：問題と解決策

| チーム開発で困ること | Git/GitHubでの解決 |
|---|---|
| 他人の変更を上書きする | ブランチで作業を分ける |
| 変更の目的が分からない | Issueとコミットに記録する |
| 未確認の変更が混ざる | PRでレビューする |
| 以前の状態に戻せない | コミット履歴から復旧する |

```text
Issue（目的）
   ↓
Branch（安全な作業場所）
   ↓
Commit（変更の記録）
   ↓
Pull Request（確認の依頼）
   ↓
main（確認済みの変更を統合）
```

## GitとGitHubの役割

| 名前 | 主な役割 | ひとことで |
|---|---|---|
| Git | PC内で変更履歴を管理する | 履歴を残す道具 |
| GitHub | 履歴を共有し、IssueやPRで協働する | チームの作業場所 |

## 最低限の用語

| 用語 | 意味 |
|---|---|
| リポジトリ | ファイルと変更履歴を管理する場所 |
| ブランチ | `main`から分けた作業用の履歴 |
| コミット | 変更をひとまとまりで記録したもの |
| PR | 変更内容のレビューと統合を依頼する場所 |
| マージ | 別のブランチの変更を統合すること |

## `main`へ直接コミットしない理由

`main`は、チームが統合済みの成果を参照する中心ブランチです。プロジェクトによっては本番へ自動デプロイされますが、**`main`と本番環境が常に同じとは限りません**。

作業ブランチとPRを使うと、変更が`main`へ入る前に次を確認できます。

- 目的がIssueと一致している
- 意図しないファイルが含まれていない
- レビューやテストが完了している

> [!IMPORTANT]
> **作業はブランチで行い、確認済みの変更だけを`main`へマージする。**

## 共有前の3点チェック

- [ ] `git status`で変更対象を確認した
- [ ] パスワードや一時ファイルを含めていない
- [ ] コミットメッセージから変更内容が分かる

> [!NOTE]
> Gitを使う目的は、履歴を綺麗に見せることではありません。変更の目的と判断材料を残し、次に作業する人が安全に前へ進める状態を作ることです。
