# 第1章：なぜGit/GitHubが必要なのか？

個人で趣味のコードを書くだけなら、自分のタイミングで保存するだけで十分です。しかし、**複数人で1つの製品（Webサイトやアプリ）を作る「チーム開発」**になると、そうはいきません。

ここでは、Git/GitHubを使う理由を「なぜやるのか」という目的から学びましょう。

---

## 1.1 個人開発とチーム開発の決定的な違い

複数人で同時に開発を進めると、以下のような問題が発生します。

* **ファイルの上書き・先祖返り問題**:
  AさんとBさんが同じファイルを同時に編集し、それぞれ自分のPCからサーバーにアップロードしたとします。後からアップロードした方の変更で上書きされ、もう片方の変更は消えてしまいます。
* **「壊れていない状態」の維持（本番環境の保護）**:
  誰かが書いた開発途中の（バグが含まれている可能性のある）コードを直接本番環境に公開してしまうと、ユーザー全員がサイトを使えなくなってしまいます。
* **「だれが・なぜ・どこを」変えたか分からない問題**:
  コードがいつの間にか書き換わっていて、誰が何のために変更したのか分からないと、バグが発生した際に原因究極ができず、誰も触れない「秘伝のソースコード」になってしまいます。

これらをすべて解決し、**「複数人で安全に、履歴を残しながらコードを育てる仕組み」**がGitとGitHubです。

---

## 1.2 例えで理解する：GitとGitHubの役割

GitとGitHubは、よく「**ノートと、学校の掲示板（図書室）**」に例えられます。

| ツール | 役割 | 例え |
| :--- | :--- | :--- |
| **Git** | あなたのPC（ローカル）でのファイルの変更履歴を記録するツール | 自分の机の上でノート（設計図）にスケッチを描き、下書きや修正の履歴を残すこと |
| **GitHub** | チーム全員のGit履歴を集めて管理する、インターネット上のWebサービス | 描いたスケッチを学校の掲示板に貼り出し、みんなで見合ったり、図書室の共有本棚にファイリングして保管すること |

> [!NOTE]
> 💡 **コラム：第1章を読み進めるためのGit用語ミニ図鑑**  
> ※具体的なコマンドや使い方は第2章以降で説明するので、今はなんとなくのイメージだけ掴めばOKです！
> 
> * **リポジトリ**：チーム全員で管理する「コードの保管庫（共有オフィス）」。
> * **ブランチ（作業部屋）**：本番用のコードを壊さないよう、各自が隔離されて作業する「専用の部屋」。
> * **main（メイン）**：本番環境にリリースする「いつでも正常に動く」コードを保管する中心的な場所。
> * **コミット（記録）**：コードの変更を履歴のセーブポイントとして「記録・保存」すること。
> * **マージ（合流）**：作業部屋（ブランチ）の変更を、本番用（main）に「合流」させること。
> * **プルリクエスト（PR：レビュー依頼）**：本番に合流させる前に、「変更したからチェックして合流させて！」とチームメンバーに送るレビュー・合流の依頼。

---

## 1.3 「直接main（本番）を書き換えてはいけない」根本的な理由

Gitでは、本番環境にリリースする（いつでも正常に動く）コードを管理する中心的な場所を **`main`（メイン）ブランチ** と呼びます。

全員がこの `main` に対して直接コードを書き換えて保存（コミット）してしまうと、以下のような大惨事が起こります。
1. バグのあるコードが混入した際、誰のどの変更が原因か特定できなくなる。
2. 他のメンバーが「最新の動くコード」を手元にダウンロードできなくなる。

そのため、チーム開発では以下の大原則があります。
> [!IMPORTANT]
> **チーム開発の大原則**
> **「本番用のブランチ（main）は常に正常に動く状態に保ち、各自は隔離された安全な別部屋（ブランチ）で作業する」**

各自が別室で作業を完成させ、リーダーやメンバーのチェック（レビュー）をクリアしたものだけを `main` ブランチに合流させることで、品質を担保します。

---

## 1.4 Git習得の前に：最も大切な「リポジトリを綺麗に保つ」意識

どれだけ便利なコマンドを覚えても、開発者に**「リポジトリ（コード保管庫）を綺麗に保つ」という当事者意識**がなければ、チーム開発は簡単に破綻します。

Gitのリポジトリは「自分のPCの一時保存フォルダ」ではなく、**「チーム全員で管理する共有のオフィス」**です。共有スペースを綺麗に保つために、以下の習慣を身につけましょう。

1. **散らかしたままコミットしない**:
   開発中の一時的なメモや、動作確認のためだけに書いたデバッグ用のコード（`console.log` など）は、コミットする前に削除するか、`.gitignore` で除外します（`.gitignore` の詳細は第2章で解説します）。
2. **こまめに掃除する（部屋を片付ける）**:
   開発が終わり、`main` に合流（マージ）された作業用ブランチは「用済みの部屋」です。放置するとブランチ一覧がゴミだらけになるため、合流後は速やかに削除します。
3. **「見られて恥ずかしくないか」を確認する**:
   変更を保存・記録（コミット）する前に、必ず何が変更されたかを確認し、「意図しないファイルが含まれていないか」「メッセージは分かりやすいか」を見直す癖をつけます（第2章で、変更状態を確認する具体的なコマンドを学びます）。

**「リポジトリの綺麗さ＝プロジェクトの安全性と品質」**です。この意識を持ってGitを使い始めましょう。

---

## 1.5 「言われた機能を作る」から「ステークホルダーへ価値を届ける」へ

開発プロジェクト（特に客先常駐や受託開発などを行うエンジニア）において陥りがちな罠が、**「言われた通りにコードを書き、指示された機能を作る」こと自体を目的にしてしまう**ことです。

しかし、Gitを使う目的の根本は、ツールの操作方法を覚えることではなく、**「あなたが関わるサービスを大切にし、そのサービスを通じてユーザーやビジネスなどのステークホルダーにきちんと価値を届けること」**にあります。

この意識の有無によって、Gitの使い方は以下のように劇的に変わります。

| 項目 | 「言われた機能を作るだけ」の人 | 「価値を届ける」ことを意識している人 |
| :--- | :--- | :--- |
| **コミットメッセージ** | `修正` `とりあえずコミット` など、自分しか分からない内容で残す。 | `fix: ログイン時のエラーハンドリングを追加し、ユーザーの離脱を防ぐ` など、意図と価値が伝わる内容で残す。 |
| **プルリクエスト（PR）** | ファイルを変更して「レビューお願いします」とだけ送り、背景や変更内容を説明しない。 | PRの説明欄に「なぜこの修正が必要なのか」「ユーザーやビジネスにどう貢献するか」「画面のスクショ」を記載し、レビュアー（ステークホルダー）の手間を減らす。 |
| **エラーやコンフリクト** | 「エラーが出たので自分にはできません」と投げ出し、誰かが直すのを待つ。 | チームメンバーと相談し、コードの競合を解消して「サービスにとって何が正しい状態か」を主体的に考えて解決する。 |
| **コードの品質と後片付け** | 動けばいいので汚いコードを放置し、マージ後のブランチも消さずに残す。 | 将来そのコードを触るメンバー（ステークホルダー）が迷わないよう、コードを整理し、不要なブランチを片付ける。 |

Gitは、あなたの**「サービスへの愛着」と「プロフェッショナルとしての仕事の丁寧さ」を映し出す鏡**です。ただ指示を消化するだけのオペレーターではなく、価値を届けるエンジニアとしてGitを使いこなしましょう。
