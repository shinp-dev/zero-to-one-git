# 第5章：トラブルシューティングとリカバリー

## この章のゴール

**症状から、安全な最初の一手を選べる。**

## まず見る：逆引き表

| 困っていること | 最初の一手 | 注意 |
|---|---|---|
| 現在の状態が分からない | `git status` | まず確認する |
| 未コミットの編集を戻したい | `git restore <ファイル>` | 編集内容は消える |
| `git add`だけ取り消したい | `git restore --staged <ファイル>` | ファイル内容は残る |
| 直前のコミット文を直したい | `git commit --amend` | push後はチームに確認 |
| 直前のコミットだけ戻したい | `git reset HEAD~1` | ファイル内容は残る |
| コンフリクトが出た | 競合ファイルを開く | 勝手に片側を捨てない |
| 秘密情報をpushした | 鍵を即時無効化する | 履歴削除より先に行う |

> [!IMPORTANT]
> 迷ったら追加のコマンドを実行せず、`git status`の結果をチームメンバーへ共有します。

## コンフリクトを解消する

```text
CONFLICT表示
    ↓
競合ファイルを開く
    ↓
関係者と正しい内容を決める
    ↓
マーカーを削除して保存
    ↓
git add → git commit
```

競合部分は次のように表示されます。

```text
 <<<<<<< HEAD
現在のブランチの内容
 =======
取り込むブランチの内容
 >>>>>>> feature/issue-13-example
```

※表示例では判別しやすいよう、マーカーの先頭に空白を入れています。実際のファイルでは行頭から表示されます。

正しい内容に編集し、3種類のマーカーをすべて削除します。

```bash
git add <直したファイル>
git commit -m "fix: コンフリクトを解消"
```

## 作業ブランチへ最新の`main`を取り込む

チームの運用でマージ方式を採用している場合の例です。

```bash
git status
git pull origin main
```

> [!NOTE]
> rebaseを使うチームもあります。共有済みの履歴を書き換える可能性があるため、チームのルールを確認してください。

## よく使う復旧操作

### 編集を戻す

```bash
git restore <ファイル名>
```

⚠️ 未コミットの編集内容が消えます。対象を確認してから実行します。

### ステージから下ろす

```bash
git restore --staged <ファイル名>
```

ファイルの編集内容は残ります。

### 直前のコミットを修正する

```bash
git add <追加するファイル>
git commit --amend -m "正しいメッセージ"
```

### 直前のコミットを取り消して編集状態へ戻す

```bash
git reset HEAD~1
```

## 履歴を書き換える操作

次の操作は、未コミットの変更やコミットを失う可能性があります。

```bash
git reset --hard <コミットID>
git push --force-with-lease origin <ブランチ名>
```

> [!WARNING]
> - `main`や共有ブランチでは実行しない
> - 自分だけが使うブランチでも、対象を再確認する
> - `-f`より、他人の更新を検知できる`--force-with-lease`を優先する

## 秘密情報をpushした

```text
1. 漏洩した鍵・パスワードを無効化／再発行
2. チーム責任者へ連絡
3. GitHub上の公開範囲と影響を確認
4. 管理者の手順で履歴から削除
5. 新しい秘密情報がGit管理外か確認
```

> [!CAUTION]
> ファイルを削除するコミットだけでは、過去の履歴から秘密情報を閲覧できます。履歴の書き換えはチーム全体へ影響するため、個人判断で共有ブランチをforce pushしないでください。
